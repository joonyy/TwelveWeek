# Twelve Week

비전 → 12주 목표 → 목표별 12주 계획 → 일간 실행 → 주간 평가를 연결하는 웹 서비스.
React/Vite 프론트, Express API, PostgreSQL DB를 사용한다. 배포 대상은 Render + Aiven이며 TheCorner와 독립된 프로젝트다.

저장소: [joonyy/TwelveWeek](https://github.com/joonyy/TwelveWeek)

실제 사용: **https://twelveweek-joonyy.onrender.com**. 2026-10-28 Render + Aiven 배포와 기존 기록 이전을 완료했다. 운영 기록과 개발용 로컬 DB는 자동 동기화되지 않는다. 접속 방법·백업·배포 검증은 [운영 배포 기록](docs/DEPLOYMENT.md)을 따른다.

## 로컬 실행

Node.js 22.12 이상, npm, 실행 중인 Docker가 필요하다.

```sh
git clone https://github.com/joonyy/TwelveWeek.git
cd TwelveWeek
cp .env.example .env # 첫 설치 때만. 기존 .env를 덮어쓰지 않는다.
npm ci
docker compose up -d --wait
npm run dev
```

터미널·AI 작업 세션을 닫아도 로컬 앱을 계속 사용하려면 `npm run dev:background`로 시작한다. 독립된 프로세스로 실행하며 로그는 Git에서 제외된 `.logs/dev.log`에 남긴다. 이미 양쪽 서버가 실행 중이면 중복 시작하지 않는다.

macOS에서는 개발용 `scripts/local-start.command`를 실행하면 Docker Desktop → 기존 DB → API·웹 서버 준비 후 브라우저를 연다. 이미 실행 중이면 같은 로컬 앱을 다시 열며 터미널을 닫아도 서버는 유지된다. 디스크 여유 공간이 1GB 미만이면 새 실행을 중단하고 안내한다. 실제 사용을 위한 바탕화면의 `TwelveWeek.command`는 운영 URL을 연다.

- 웹: http://127.0.0.1:5178
- API 상태: http://127.0.0.1:4110/api/health
- Docker DB: localhost:55439, `twelve_week`. 로컬 개발용 자격증명은 compose.yaml에 있다.
- API 시작 시 SQL migration을 자동 적용한다. 실패하면 서버를 열지 않는다.
- `docker compose stop`으로 DB를 멈출 수 있다. `down -v`는 저장 데이터를 삭제하므로 보존할 때 사용하지 않는다.

장기·3년 비전은 목록 입력을 기본으로 하며 자유 서술로 바꿀 수 있다. 새 계획에는 빈 목표 3개를 미리 준비하고, 모범 주간은 시간축 캘린더로 작성한다. 책임과 헌신은 정리본의 네 가지 태도 및 7영역 바퀴 구조를 따른다.

장기비전 옆 **AI와 비전 다듬기**에서 대화 저장·재개, 선택한 외부 대화 가져오기, 비전 수정 권한·이력·되돌리기를 지원한다. ChatGPT·Claude용 MCP와 선택형 로컬 Codex resume도 준비했다. 실제 AI를 사용하려면 API 키/모델 또는 로컬 Codex 연결이 필요하다. [연결 설정과 지원 범위](docs/AI_INTEGRATION.md)를 참고한다.

첫 화면에서 유저를 만들거나 선택한다. 기본 주기는 2026-10-05~12-27이며 초안에서 월요일 시작일과 **실행 주수(1~12주)**를 바꿀 수 있다. 예를 들어 2026-10-12 시작·11주 실행이면 종료일은 12월 27일, 회고 주간은 12월 28일~2027년 1월 3일이다. 작성 중인 내용은 **저장** 버튼으로 보관한다. 착수는 목표·전술·1회 완료 조건·실행 주차가 준비되면 가능하다. 착수 후 기간 축소는 미래 주만 제외하며 이미 시작한 주의 기록·점수 기준은 유지한다.

## 검증

실제 앱 데이터와 테스트 DB를 분리한다. 테스트 명령은 이름이 `_test`로 끝나는 DB만 허용하며 테스트 테이블을 초기화한다. 두 DB 테스트 명령을 동시에 실행하지 않는다.

```sh
docker compose exec -T db psql -U twelve -d postgres -c 'CREATE DATABASE twelve_week_test'
npm test
npm run test:api
npx playwright install chromium
npm run test:e2e
npm run build
```

테스트 DB가 이미 있으면 생성 명령은 생략한다. 브라우저 테스트는 별도 포트 4111·5179를 사용하므로 실제 로컬 앱(4110·5178)을 켜둔 상태에서도 실행할 수 있다. 테스트 서버의 시계는 2026-10-07로 고정되며, 실제 API에는 시계 변경 기능이 없다. 스크린샷은 `test-results/`에 생성된다. GitHub Actions 검사 구성도 포함했다.

## Render + Aiven 배포 준비

GitHub 저장소는 [joonyy/TwelveWeek](https://github.com/joonyy/TwelveWeek)다. 현재 전용 Aiven DB와 Render 서비스가 연결돼 있다. 아래 순서는 새로운 환경에 재구성할 때의 절차다.

1. **전용 Aiven PostgreSQL** 서비스와 앱용 DB를 생성한다. 기존 TheCorner DB를 재사용하지 않는다. 연결 URI와 해당 서비스 CA 인증서를 준비한다.
2. 저장소를 Render Blueprint로 연결하여 `render.yaml`을 적용한다. API는 Node Web Service, 프론트는 Static Site다.
3. API 환경변수에 `DATABASE_URL`, `DATABASE_SSL=true`, `DATABASE_CA_PEM`(인증서 PEM 전문)을 넣는다. `WEB_ORIGIN`은 프론트의 정확한 HTTPS origin이다. 여러 origin이 필요하면 쉼표로 구분한다.
   인증은 사용자별 이름과 비밀번호를 사용한다. 비밀번호는 사용자마다 다른 salt를 사용하는 scrypt 해시로 저장한다. 기존 비밀번호 없는 DB를 처음 업그레이드할 때만 `INITIAL_PROFILE_PASSWORD`를 별도 지정해 migration을 먼저 실행하며, 운영 초기값을 소스나 문서에 기록하지 않는다. 이후 재시작이나 migration 재실행은 기존 비밀번호를 바꾸지 않는다. `/api/health`는 상태 확인을 위해 공개한다.
4. 프론트 `VITE_API_BASE_URL`에 API의 HTTPS origin을 넣는다. `/api`는 붙이지 않는다. 프론트 변수는 빌드 시 반영되므로 바꾸면 재빌드한다. DB URI·인증서·토큰을 `VITE_` 변수에 넣지 않는다.
5. 양쪽 URL이 확정되면 `WEB_ORIGIN`과 `VITE_API_BASE_URL`을 맞추고 API `/api/health`, 프로필 생성, 계획 저장, 새로고침 후 복원, 캘린더 다운로드를 실서비스에서 다시 검증한다.

환경값 예시는 `.env.example`에 있다. `DATABASE_CA_PATH`로 Render Secret File을 사용하는 것도 가능하다. PEM 문자열의 실제 줄바꿈 및 리터럴 `\n` 모두 지원한다. TLS 인증서 검증은 끄지 않는다. Aiven 연결법은 [공식 Node.js 안내](https://aiven.io/docs/products/postgresql/howto/connect-node)를 따른다.

프론트는 CDN에서 제공하는 정적 사이트로 구성했다. 깨우기 요청은 API `/api/health`에 보내면 된다. `KEEPALIVE_URLS`에 URL을 쉼표로 넣으면 프론트도 함께 확인할 수 있다. [Render 서비스 유형](https://render.com/docs/service-types), [무료 Web Service 동작과 사용량 제한](https://render.com/docs/free)을 확인한다. 외부 요청은 유휴 종료 대응이며 무료 인스턴스 시간 한도나 재시작까지 없애지는 않는다.

외부 cron에서 `node scripts/keepalive.js`를 실행하거나, GitHub repository variable `KEEPALIVE_URLS`를 설정해 준비한 10분 간격 workflow를 활성화한다. 변수 미설정 시 작업은 건너뛴다. GitHub의 예약 작업은 지연될 수 있으며 전용 유료 Render Cron Job은 생성하지 않았다. 개인 저장소에서 사용할 Actions 실행량은 실제 배포 시 확인한다.

## 이번 주로 캘린더 파일 가져오기

**실행과 평가 → 이번 주 계획표 / 주간 일정 → 캘린더 가져오기**에서 `.ics` 파일을 읽는다. Mac 캘린더 왼쪽에서 해당 캘린더를 선택하고 **파일 → 내보내기 → 내보내기**로 저장하면 ‘나의 Mac’ 일정도 사용할 수 있다. [Apple 안내](https://support.apple.com/guide/calendar/icl1023/mac).

선택한 주의 일정만 미리 보여주고 원하는 항목을 근무·고정 일정 블록으로 복사한다. 종일 일정은 직접 선택하며, 기존 근무·배치한 실행·선택한 일정끼리의 겹침은 확인 후 함께 적용할 수 있다. 다른 주와 기본 모범 주간, 전술 횟수·완료·평가는 보존한다. 저장 전 시간표 변경이 있다면 먼저 저장하거나 취소한다. 같은 파일에서 이미 가져온 블록은 중복 추가하지 않는다. 원본 파일은 브라우저에서 처리하고 선택한 블록만 저장한다.

1MB 이하의 `.ics`를 지원하며 `.icbu` 아카이브는 지원하지 않는다. 반복 일정과 파일에 정의된 시간대를 해석하고, 정의 없는 시간대·너무 많은 반복·‘이후 모든 반복’ 예외 등은 오류를 표시한다. 이 경우 기간을 줄이거나 iCloud 연결을 사용할 수 있다. 04시 경계와 12시간 최대 블록 길이에 맞춰 긴 일정을 나눠 저장한다. 이후 원본 일정의 수정·삭제는 자동 동기화하지 않는다.

같은 창의 **iCloud 연결**에서 아래의 기존 일정 비교·전술 배치 흐름도 열 수 있다.

## iCloud 캘린더 비교·반영

1. 계획 화면에서 **주차별 → Apple Calendar와 비교**를 연다. 저장 전 변경이 있으면 버튼에 표시된 대로 계획부터 저장한다.
2. Apple 계정 이메일과 [Apple에서 생성한 앱 전용 암호](https://support.apple.com/ko-kr/102654)를 앱의 연결 화면에 직접 입력한다. 암호를 대화나 저장소에 기록하지 않는다. 서버에는 암호화해 저장한다.
3. 비교할 캘린더와 새 일정을 넣을 캘린더를 선택하고 기존 일정을 불러온다. iCloud에 동기화된 일정이 대상이며 Mac에만 저장된 캘린더나 다른 제공자의 계정은 포함하지 않는다.
4. 실행을 고른 뒤 캘린더에서 클릭·드래그하거나 회차별 날짜·시각·길이를 입력한다. 겹치면 시간을 옮기거나, 겹쳐 적용을 선택하거나, 기존 일정 안에 실행을 연결한다. 연결은 원본 제목·시간을 유지하며 실행 체크는 각각 남는다.
5. **적용 전 검토**에서 변경 목록을 확인하고 적용한다. 초안의 배치는 착수할 때 이어지며 전술 횟수·완료 상태는 바뀌지 않는다.

`CALENDAR_SECRETS_KEY`는 32자 이상의 안정된 서버 비밀값으로 설정한다. 생략하면 기존 `AI_SECRETS_KEY`를 사용한다. Render Blueprint에는 별도 생성 설정이 있다. 연결 해제는 저장한 연결 정보를 지우며 Apple의 일정은 지우지 않는다.

적용 직전에 기존 일정과 계획 버전을 다시 확인한다. 외부 서비스와 DB를 하나의 트랜잭션으로 묶을 수는 없으므로 일부만 반영된 경우 처리 항목을 표시하고 다시 불러오도록 한다. 이번 기능은 불러오기·비교·선택 반영이며, 이후 앱에서 일정을 옮기는 동작과 Apple Calendar의 자동 양방향 동기화는 별도 범위다. 실제 계정 연결·수정 결과는 사용자가 앱 전용 암호를 연결한 뒤 확인해야 한다.

## 사용자 선택 방식

이 브라우저에서 처음 인증하는 계정은 이름 목록에서 유저를 선택한 뒤 비밀번호로 로그인한다. 사이트 공통 접속키는 사용하지 않는다. 새 유저는 이름과 비밀번호를 함께 설정하며, 로그인한 뒤 사이드바의 `계정 설정` → `비밀번호 재설정`에서 현재 비밀번호를 확인하고 변경할 수 있다. 변경 시 현재 기기의 세션은 유지하고 다른 기기의 로그인 세션은 만료한다.

로그인한 계정은 이 브라우저에서 인증 세션을 기억한다. `유저 전환`은 세션을 종료하지 않고 계정 선택 화면을 열며, 기억된 계정을 고르면 서버에서 유효성을 확인한 뒤 비밀번호 없이 연결한다. 새로고침·같은 브라우저 재실행 뒤에도 이어서 사용하며 기존 로그인도 자동으로 기억한다. `로그아웃`은 해당 계정의 기억을 지우고 현재 세션을 종료한다. 서버 연결이 끊겨도 이 브라우저의 기억은 지운다. 다른 기기·브라우저는 처음 한 번 비밀번호로 로그인해야 한다. 비밀번호 원문은 저장하지 않으며 만료되거나 철회된 세션은 다시 인증한다. 여러 탭은 각자 선택한 계정의 토큰을 사용해 다른 탭의 계정 전환이 저장 대상에 영향을 주지 않는다.

`계정 설정`의 `계정 삭제`에서는 본인 이름·현재 비밀번호·삭제 확인을 입력한 뒤 계정과 모든 앱 기록을 삭제할 수 있다. 서버는 로그인한 계정만 삭제하며 주기·실행·평가·독서 기록·AI 대화·저장된 연결 정보와 모든 세션/OAuth 승인을 한 트랜잭션으로 정리한다. 다른 사용자와 공유 OAuth 클라이언트 등록은 보존한다. 외부 캘린더·블로그에 내보낸 내용은 지우지 않는다. 비밀번호를 잊은 상태의 이메일 복구는 제공하지 않는다.

잘못 만든 주기는 `나의 12주`의 작성 중인 카드 아래 `초안 삭제`에서 제목·기간을 확인하고 삭제한다. 서버는 소유자·상태·버전을 확인하며 실행 기록이 있는 초안, 실행 중인 주기와 완료 주기는 이 경로로 삭제하지 않는다. 다른 화면에서 바뀐 초안은 목록을 새로 불러온 뒤 다시 확인해야 한다.

- 32바이트 임의 세션 토큰, 기본 만료 365일(`TOKEN_TTL_DAYS`, 1~730일).
- DB에는 토큰 해시만 저장하고 브라우저는 localStorage에 토큰을 보관한다.
- 유저 전환 시 현재 토큰을 폐기한다. 다른 기기의 세션은 유지한다.
- 이름 목록은 공개되지만 비밀번호 확인 없이 해당 사용자의 로그인 세션을 발급하지 않는다. 비밀번호와 해시는 API 응답·브라우저 저장소에 보관하지 않는다.
